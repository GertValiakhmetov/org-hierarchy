# Орг-структура компании

Дашборд для мониторинга иерархии «дивизионы → отделы → команды»: интерактивное
дерево и аналитическая таблица с агрегированными показателями.

**Стек:** React 19, Vite 7, TypeScript, styled-components, TanStack Query.
Бэкенд — Node + Express, данные генерируются в памяти.

## Запуск

```bash
npm install
npm run dev
```

Клиент — <http://localhost:5173>, API — <http://localhost:4000>.
Запросы к `/api` из клиента проксирует Vite, поэтому клиентский код всегда
обращается по относительному пути и не знает адреса бэкенда.

### Скрипты

| Команда | Что делает |
| --- | --- |
| `npm run dev` | Поднимает сервер и клиент одной командой |
| `npm run build` | Проверка типов + production-сборка клиента |
| `npm run test` | Unit-тесты (vitest) |
| `npm run typecheck` | Проверка типов клиента и сервера |

### Переменные окружения сервера

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PORT` | `4000` | Порт API |
| `API_LATENCY_MS` | `250` | Искусственная задержка ответа — без неё состояние загрузки не увидеть |
| `LIVE_TICK_MS` | `3000` | Как часто сервер меняет случайный узел и рассылает патч |

## Панель отладки

В правом нижнем углу — панель, переключающая поведение сервера. Это инструмент
для проверки нефункциональных требований, а не часть продукта.

| Режим | Что отдаёт сервер |
| --- | --- |
| Обычный ответ | Штатные данные |
| Медленный ответ (5 с) | Те же данные с задержкой — видно скелет загрузки |
| Пустой ответ | `[]` |
| Ошибка 500 | HTTP 500 |
| Невалидная схема | Объект без обязательных полей |

Режим хранится на сервере, а переключение инвалидирует кэш без перезагрузки
страницы. Благодаря этому виден переход, а не только конечное состояние —
в частности то, ради чего панель и сделана: при включении «Ошибка 500» уже
загруженное дерево **остаётся на экране**, а сверху появляется полоса о неудачном
обновлении. Подробнее — [ADR 003](docs/adr/003-debug-modes.md).

Отдельная кнопка «Разорвать соединение» обрывает WebSocket — так видно
индикатор переподключения и backoff.

Убрать панель из сборки: `VITE_DEBUG_PANEL=false npm run build`.

## Возможности

- **Дерево** — раскрытие ветвей, второй уровень открыт по умолчанию, суммарная
  численность и цветовой индикатор эффективности на каждом узле.
- **Таблица** — подразделение, уровень, всего сотрудников, суммарный бюджет,
  средневзвешенная эффективность. Сортировка по любому столбцу (повторный клик
  разворачивает порядок), фильтр по названию с дебаунсом 250 мс.
- **Связь представлений** — клик по строке таблицы выделяет узел в дереве и
  раскрывает ведущую к нему ветвь; клик по узлу дерева подсвечивает строку.
- **Раскладка** — от 1280 px дерево и таблица показаны рядом, ниже переключаются
  кнопками «Дерево / Таблица».
- **Живые обновления** — сервер шлёт частичные патчи по WebSocket, клиент
  применяет их без рефетча. Изменившиеся ячейки подсвечиваются и гаснут за 1,5 с
  — у самого узла и у его предков, чьи суммы сдвинулись.
- **Соединение** — индикатор в шапке, переподключение с экспоненциальным backoff
  и джиттером. После обрыва данные перезапрашиваются только если версия на
  сервере успела измениться.
- **Клавиатура** — по таблице: `↑` `↓` перемещают фокус, `Home` и `End` — к
  началу и концу, `Enter` выделяет узел и раскрывает ведущую к нему ветвь.

## AI в разработке

Инструмент: **Claude Code (Opus 5)**. Раздел пополняется по ходу этапов.

### Что сгенерировано

Весь код этапа 1 написан моделью по постановке из задания: генератор данных
сервера, Express-слой, валидатор схемы, построение дерева, компоненты дерева и
состояний, тема и стили, тесты.

### Что переписано руками и почему

- **Численность в дереве.** Сгенерированная версия показывала собственный
  `headcount` узла — буквально по тексту задания. На практике это читалось как
  «в отделе 2 человека», хотя в его командах работали ещё 43. Переведено на
  суммарный показатель, см. [ADR 004](docs/adr/004-aggregate-in-tree.md).
- **Протечка внутренних полей агрегации.** Первая версия `aggregateTree`
  возвращала накопитель напрямую, и промежуточные суммы (`weighted`,
  `nodeCount`) оказывались в публичном результате — TypeScript их скрывал, но в
  рантайме они были. Накопитель отделён от результата; поймано тестом.
- **Повтор запроса по кнопке.** Кнопка «Повторить» шла через `refetch()` и
  подчинялась политике автоповторов: один клик давал три запроса и четыре
  секунды неактивной кнопки. Разведены автоматические повторы (нужны при
  фоновом обновлении) и явный клик — теперь ровно один запрос.

- **Слой данных.** Модель предлагала написать собственный кэш (~150 строк:
  stale-while-revalidate, дедупликация, отмена). Выбран TanStack Query:
  требование задания — корректное кэширование, а не факт самописной реализации,
  и готовое решение здесь надёжнее. Обоснование — [ADR 001](docs/adr/001-data-layer.md).
- **Механизм отладки состояний.** Первая версия принимала `?scenario=` в адресе
  страницы и подмешивала его в ключ кэша. Переделано на серверное переключение
  режима: прежний вариант создавал *отдельный* запрос с пустым кэшем и потому не
  мог воспроизвести главное состояние — отказ обновления при уже показанных
  данных. При переделке выяснилось, что эта ветка кода была разобрана неверно:
  экран ошибки рисовался поверх дерева. См. [ADR 003](docs/adr/003-debug-modes.md).
- **Прокси WebSocket.** Сгенерированная конфигурация Vite не содержала
  `ws: true`, и сокет молча не подключался — индикатор навсегда оставался в
  состоянии «подключение…». Поймано прогоном в браузере, тестами такое не
  ловится.
- **Мемоизация строк таблицы.** При добавлении клавиатурной навигации я
  передал каждой строке инлайновый обработчик, что свело на нет мемоизацию
  (замер показывал 51 перерисовку вместо 2). Переписано на делегированный
  обработчик на `tbody`, пропсы строк снова стабильны.
- **Форматирование чисел.** Первая версия выводила «51 подразделений» и «67,0»
  для целого показателя. Добавлены склонение по числу через `Intl.PluralRules`
  и правило «целые — без дробной части, средневзвешенные — с одним знаком».
- **Тест порядка узлов.** Сгенерированный тест утверждал, что порядок обхода не
  зависит от порядка узлов в ответе. Это неверно: порядок соседних узлов
  сознательно наследуется от сервера, независимо только разрешение связи
  «ребёнок встретился раньше родителя». Тест разбит на два и переписан под
  фактический контракт.
### Как проверялось

Ни один сгенерированный фрагмент не принимался без проверки: `npm run typecheck`
и `npm run test` на каждом шаге, плюс разовый сквозной прогон валидатора и
построения дерева на реальном ответе сервера (51 узел, 4 корня, 3 уровня) —
он подтвердил, что контракт `shared/types.ts` соблюдают обе стороны.
