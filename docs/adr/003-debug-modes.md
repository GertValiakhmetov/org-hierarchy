# ADR 003. Отладочные режимы на сервере, а не в параметрах запроса

**Статус:** принято · этап 1 (заменяет первоначальное решение того же этапа)

## Контекст

Этап 1 требует обрабатывать состояния загрузки, ошибки и пустого ответа.
Исправно работающий сервер ни ошибки, ни пустоты не возвращает, поэтому нужен
способ вызвать их намеренно — и для ручной проверки, и для демонстрации.

Первая реализация принимала `?scenario=error` в адресе страницы и пробрасывала
его в запрос: `GET /api/org-tree?scenario=error`.

## Проблема первого решения

Параметр входил в ключ кэша — `['org-tree', 'error']`. Это **другой запрос**,
а не тот, которым живёт приложение, и у него всегда пустой кэш. Как следствие,
воспроизводился только один сценарий из трёх интересных:

| Ситуация | Воспроизводилась? |
| --- | --- |
| Отказ при первой загрузке, показывать нечего | да |
| Отказ фоновой ревалидации при уже показанных данных | **нет** |
| Переход рабочее состояние → отказ → восстановление | **нет**, требовалась перезагрузка страницы |

Вторая строка — именно то, что проверяет требование надёжности: данные уже на
экране, обновление не удалось. Проверено, что TanStack Query в этом случае
сохраняет `data` и переводит запрос в `status: 'error'` одновременно, то есть
различать «ошибка без данных» и «ошибка поверх данных» обязан клиент. Пока
механизм отладки до этого состояния не доставал, ветка кода была ненаблюдаемой —
и, как выяснилось при переделке, отрисовывала экран ошибки поверх дерева.

## Решение

Режим хранится на сервере и переключается отдельным эндпоинтом:

```
GET  /api/debug/mode          → { mode }
POST /api/debug/mode { mode } → { mode }
```

Клиент продолжает ходить тем же `GET /api/org-tree` с единственным ключом кэша.
Панель в углу экрана меняет режим и делает `invalidateQueries`, без перезагрузки
страницы, поэтому видны именно переходы между состояниями.

Режимы: `normal`, `slow` (5 с — чтобы рассмотреть скелет), `empty`, `error`,
`invalid` (ответ, не проходящий валидацию схемы).

## Альтернативы

**Оставить `?scenario=`.** Отклонено по причинам выше: ключевое состояние
недостижимо.

**MSW (Mock Service Worker).** Перехват на уровне сети даёт ту же гибкость, но
это заметная зависимость ради инструмента разработки, и она подменяет сервер —
то есть перестаёт проверять настоящий контракт между клиентом и API.

**Гасить сервер вручную.** Показывает только отказ сети и не воспроизводит ни
пустой ответ, ни нарушение схемы.

## Последствия

- На сервере появляется изменяемое состояние. Оно одно, процесс-локальное и
  влияет только на отладочные эндпоинты.
- Панель включена и в production-сборке: иначе проверяющий, запустивший
  `docker-compose up` (этап 4), до состояний не доберётся. Отключается сборкой
  с `VITE_DEBUG_PANEL=false`: 98,46 → 97,40 КБ gzip. Флаг подставляется на этапе
  сборки, поэтому часть кода отбрасывается, но не весь — условие проверяется в
  рантайме, ради того чтобы панель работала и в production-сборке.
- На этапе 3 та же панель получает разрыв WebSocket-соединения — иначе
  требуемые индикатор соединения и экспоненциальный backoff не показать.
