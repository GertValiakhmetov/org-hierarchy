# ADR 007. AI-поиск: модель возвращает фильтр, а не результат

**Статус:** принято · этап 4

## Контекст

Требование: «строка поиска принимает естественный язык; ответ — структурированный
фильтр на клиенте; fallback — текстовый поиск».

Данные: 51 узел, у каждого название из двух слов и три числа. Запросы —
предикатные: «отделы больше 30 человек с эффективностью ниже 65».

## Решение

Сервер отправляет модели текст запроса и описание полей, получает **фильтр**, и
клиент применяет его к данным, которые у него уже есть.

```
«отделы больше 30 человек с эффективностью ниже 65»
   ↓ POST /api/search
{ levels: ['department'], headcount: { min: 30 }, performance: { max: 64 } }
   ↓ клиент
две строки в таблице, три снимаемых чипса
```

Три следствия, ради которых выбрана именно такая форма:

- **Цифры компании модели не уходят.** Численность, бюджеты и эффективность
  остаются на сервере. Наружу идут текст запроса и список названий.
- **Модель не может подделать данные.** Она порождает только фильтр, а он
  применяется к уже провалидированным числам. Максимум вреда — неудачная выборка.
- **Результат виден и обратим.** Фильтр показывается чипсами, каждое условие
  снимается отдельно. Ранжированный список так не умеет.

### Названия в промпте

Список из 51 названия отправляется вместе с запросом. Это осознанный размен:
без него «продажники» не превратится ни во что осмысленное, с ним — в выборку
трёх команд отдела продаж, чего поиск по подстроке не может в принципе. Наружу
уходит структура компании; числовые показатели — нет.

### Structured outputs, а не tool use

Изначально планировался вызов инструмента. Справочник по Claude API указывает
на более прямой путь: когда вызов существует только ради JSON, следует
использовать `output_config.format`. Схема описана на Zod, SDK валидирует ответ
сам. Все поля объявлены `nullable`, а не необязательными: структурированный
вывод требует полную схему, и `null` — это способ модели сказать «условия нет».

## Альтернативы

**Векторная база и retrieval.** Отклонено по четырём причинам. Задание прямо
исключает БД. Эмбеддинги не кодируют «больше 30» — предикатный запрос ими не
выражается, и разбор всё равно понадобился бы. Индексировать нечего: у узла нет
прозы, только имя из двух слов. И главное — 51 название это около 300 токенов,
то есть вся структура помещается в промпт целиком; retrieval решает проблему
«данных больше, чем влезает в контекст», которой здесь нет.

**Локальный разбор шаблонов** («больше N человек», «отделы»). Работал бы без
ключа и без интернета, и проверяющий увидел бы фичу в любом случае. Отклонено
как избыточное при наличии рабочего ключа.

**Два адаптера — Anthropic и OpenAI-совместимый.** Обсуждалось ради
проверяющего с другим провайдером, отклонено: требования такого нет, а второй
адаптер невозможно прогнать живьём.

**OpenRouter как единственный провайдер.** Рассматривался: шлюз говорит на
OpenAI-совместимом протоколе, а `z.toJSONSchema()` из zod 4 превращает нашу же
схему в JSON Schema без новых зависимостей, так что переход был бы недорогим.
Отклонено по двум причинам. Соблюдение схемы у него зависит от того, какой
апстрим-провайдер обслужит запрос: часть считает её лишь подсказкой. Это
лечится `provider.require_parameters: true`, но гарантия всё равно становится
условной. И запрос проходит через дополнительного посредника — при том что
числовые показатели мы намеренно держим на сервере.

## Границы кода, привязанного к провайдеру

Файл разделён надвое, и граница проходит не по объёму, а по переносимости:

| `search-filter.ts` (78 строк) | `anthropic.ts` (72 строки) |
| --- | --- |
| Схема фильтра на Zod | Импорты SDK, идентификатор модели |
| Текст инструкций | `messages.parse()`, разбор ответа |
| Сборка списка узлов | Классы ошибок SDK |
| Снятие `null` из ответа модели | Таймаут и повторы |

Разделение сделано не ради гипотетической замены провайдера, а ради
тестируемости: `toOrgFilter` и `buildSystemPrompt` стали чистыми функциями и
покрыты 18 тестами без сети и без моков SDK. До этого на серверном AI-пути
тестов не было вовсе. Побочно это делает замену провайдера правкой одного файла.

## Модель

`claude-haiku-4-5` — по решению заказчика. Смена модели оказалась не только
строкой с идентификатором:

| | Opus 5 | Haiku 4.5 |
| --- | --- | --- |
| `output_config.effort` | Работает | **400** — параметр убран |
| Минимум кэшируемого префикса | 512 токенов | 4096 токенов |
| Цена за млн токенов | $5 / $25 | $1 / $5 |

Системный промпт — около 2200 токенов, то есть ниже порога кэширования Haiku.
Маркер `cache_control` убран: он бы молча ничего не делал. Замеренная стоимость —
**около $0,0025 за запрос**, входные токены доминируют (13 352 против 309
выходных на шести запросах).

## Последствия

- **Ответ модели — недоверенный вход.** Он проходит `search.schema.ts` наравне с
  любым ответом API: незнакомые ключи отбрасываются, диапазоны проверяются по
  границам предметной области, перевёрнутый диапазон отклоняется. Тест
  `drops keys the filter does not define` проверяет это на `shellCommand` в ответе.
- **Три уровня отката.** Нет ключа → сервер отвечает `source: 'text'`; модель
  недоступна, отклонила запрос или не уложилась в 20 секунд → то же самое с
  `reason: 'failed'`; сервер недоступен → клиент фильтрует локально. Интерфейс
  каждый раз пишет, каким путём получен результат, и никогда не приписывает
  результат модели.
- **Ключ только на сервере.** В клиентский бандл он не попадает по устройству:
  вызов идёт с сервера, `.env` в `.gitignore`, в образ не копируется.
- **Модель вызывается по Enter, а не при наборе.** Печать фильтрует локально с
  дебаунсом 250 мс; обращение к сети на каждое нажатие было бы и медленным, и
  платным. Одинаковые запросы кэшируются на клиенте пять минут.
- **Диапазоны включающие, строгого неравенства в контракте нет.** «Ниже 65»
  модель превращает в `max: 64` — верно для целых, но `performance` у агрегатов
  дробный, и подразделение с 64,5 выпадет из выборки. Лечится добавлением
  признака исключающей границы; пока не требовалось.
