# ADR 001. Слой данных: TanStack Query вместо собственного кэша

**Статус:** принято · этап 1

## Контекст

Нефункциональные требования задают поведение слоя данных: кэширование ответов,
stale-while-revalidate с окном 5 секунд, отсутствие лишних запросов, отмена при
размонтировании компонента, инвалидация только при реальном изменении данных.

Задание не оговаривает реализацию. Объём приложения — один основной запрос и
поток точечных обновлений (этап 3).

## Решение

Использовать TanStack Query. Требуемое поведение выражается его штатными
средствами:

| Требование | Реализация |
| --- | --- |
| Кэширование | `queryKey` + `gcTime` |
| Stale-while-revalidate, 5 с | `staleTime: 5_000` |
| Отмена при размонтировании | `signal` из `queryFn` передаётся в `fetch` |
| Нет лишних запросов | Дедупликация одинаковых ключей из коробки |
| Инвалидация только при изменении | `setQueryData` для патчей, `invalidateQueries` — только по факту изменения (этап 3) |

Бессмысленные повторы отключены отдельно: ответ, не прошедший валидацию схемы,
и ошибки 4xx не ретраятся — повтор даст тот же результат.

## Альтернативы

**Собственный кэш (~150 строк).** Карта `ключ → {данные, время, запрос}`,
дедупликация параллельных запросов, `AbortController`, подписка компонентов.
Отклонено: задание проверяет корректность кэширования, а не факт самописной
реализации. Свой слой пришлось бы доводить до той же надёжности в тех местах,
которые видны не сразу — гонка при одновременном монтировании двух потребителей,
корректная отмена только последнего подписчика, поведение при ошибке во время
фоновой ревалидации.

**Без кэша, `useEffect` + `fetch`.** Не удовлетворяет требованиям: нет ни
stale-while-revalidate, ни дедупликации.

## Последствия

- Зависимость 13,3 КБ gzip (измерено). Бюджет сборки этапа 4 (≤ 200 КБ gzip) сохраняется с
  большим запасом: текущая сборка — 97 КБ gzip.
- Поведение кэша задаётся конфигурацией, а не кодом, поэтому вынесено в
  `app/providers.tsx` с объяснением каждого параметра.
- На этапе 3 живые обновления кладутся в кэш через `setQueryData`: полный
  рефетч при патче не нужен, что прямо отвечает требованию «инвалидация только
  при реальном изменении данных».
