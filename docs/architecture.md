# Архитектура

## Состав

```
client/   React-приложение (Vite, TypeScript, styled-components)
server/   Express-сервер с данными в памяти
shared/   Контракт API — единственный общий модуль
```

`shared/types.ts` подключают обе стороны, поэтому изменение формы ответа
ломает сборку сразу у сервера и у клиента, а не в рантайме.

## Слои клиента

Зависимости направлены строго вниз: слой знает о нижних и ничего не знает о верхних.

```
app/        композиция: провайдеры, тема, страница
   ↓
features/   поведение: раскрытие ветвей, дерево (далее — таблица, live)
   ↓
entities/   доменная модель: узел, дерево, полосы эффективности
   ↓
shared/api/ ресурсы: что запрашиваем, как валидируем, как кэшируем
   ↓
shared/transport/  агностика: как перемещаются байты и как называется отказ
```

| Каталог | Ответственность |
| --- | --- |
| `shared/transport` | `fetchJson`, таксономия отказов, отмена. В step/3 — WebSocket |
| `shared/api` | Описания запросов и правила валидации, по файлу на ресурс |
| `shared/lib` | Форматирование чисел, денег и дат под `ru-RU` |
| `shared/ui` | Карточка с прокруткой, переключатель, состояния, индикатор эффективности |
| `entities/org` | `OrgNode`, `OrgTree`, построение дерева, пороги эффективности |
| `features/org-structure` | Сборка модели: запрос → дерево → агрегаты, статус экрана |
| `features/org-tree` | Компоненты дерева, раскрытие ветвей и выделение |
| `features/org-table` | Таблица, сортировка, фильтрация, чипсы условий |
| `features/ai-search` | Отправка запроса на разбор и применение фильтра |
| `features/debug-panel` | Переключение режимов сервера для проверки состояний |
| `app` | `QueryClient`, `ThemeProvider`, глобальные стили, страница |

## Поток данных от API до UI

```
GET /api/org-tree
      │  плоский массив узлов
      ▼
fetchJson(path, signal)                shared/transport/http.ts
      │  unknown  — либо ApiError('network' | 'http' | 'malformed')
      ▼
parseOrgTreeResponse(payload)          shared/api/org-tree.schema.ts
      │  OrgNodeDto[]  — либо ApiError('schema') с перечнем несоответствий
      ▼
TanStack Query (ключ ['org-tree'], staleTime 5 c)
      │  кэш: мгновенная отдача + фоновая ревалидация
      ▼
buildTree(nodes)                       entities/org/build-tree.ts
      │  OrgTree { roots, byId, order }  — мемоизировано по ссылке на данные
      ▼
aggregateTree(tree)                    entities/org/aggregate.ts
      │  Map<id, OrgAggregate>          — один проход, мемоизировано по дереву
      ├──────────────┬─────────────────────┐
      ▼              ▼                     ▼
OrgTree        useTableRows → OrgTable   шапка: итог по компании
```

Агрегация считается один раз на набор данных и раздаётся всем потребителям
одной и той же картой. Дерево и таблица показывают одни и те же числа не
потому, что так написаны две реализации, а потому что реализация одна.

Ключевые свойства этого потока:

- **Сеть в одном месте.** `fetch` вызывается только в `shared/transport/http.ts`.
  Компоненты не знают ни про URL, ни про статусы, ни про `AbortSignal`.
- **Тип сужается по мере подъёма.** `fetchJson` возвращает `unknown`, а не
  generic `<T>`: из `unknown` нельзя ничего достать, не сузив тип, поэтому
  единственный путь к `OrgNodeDto[]` лежит через валидатор. Обещание
  `fetchJson<OrgNodeDto[]>()` было бы неправдой — компилятор поверил бы на слово.
- **Вид ошибки соответствует уровню, который её установил.** Транспорт может
  утверждать только то, что видит: `network` — не дошли, `http` — статус не-OK,
  `malformed` — тело не разобралось как JSON. Вердикт `schema` выносит
  исключительно валидатор, и только он несёт `issues` с путями полей.
- **Невалидный ответ — ошибка.** Данные, не прошедшие схему, не доходят до
  модели: `parseOrgTreeResponse` бросает `ApiError`, и UI показывает состояние
  ошибки с конкретными путями полей.
- **Отмена при размонтировании.** `signal` приходит из `queryFn` и передаётся в
  `fetch`, поэтому уход со страницы обрывает HTTP-запрос, а не просто
  игнорирует его результат.
- **Дерево строится один раз на ответ.** `buildTree` обёрнут в `useMemo` по
  `query.data`: фоновая ревалидация, вернувшая те же данные, не пересобирает
  структуру.

## Роль `app/app.tsx`

Страница только собирает — четыре вызова и разметка:

```tsx
const org = useOrgStructure();
const navigation = useTreeNavigation(org.tree);
const table = useTableRows(org.tree, org.aggregates);
const [view, setView] = useState<View>('tree');
```

Ни одной вычисляющей строки в файле нет: всё, что считается, живёт в хуках с
именами. Дальше по этому пути не идём сознательно — композиция и есть работа
страницы, а вынос её в контейнер или контекст только добавил бы прыжок.

`useOrgStructure` отдаёт размеченное объединение, а не набор булевых флагов:

```ts
type OrgStructure = ... & ({ status: 'ready'; tree: OrgTree } | { status: ...; tree?: OrgTree })
```

Поэтому после проверки `org.status !== 'ready'` компилятор знает, что `org.tree`
определено, и разметка обходится без утверждений типа.

`useTreeNavigation` объединяет раскрытие ветвей и выделение потому, что они
связаны: выбор узла из таблицы обязан раскрыть ведущую к нему ветвь, а
клавиатурная навигация (этап 3) читает и то и другое одновременно.

## Перерисовки таблицы

`OrgTableRow` мемоизирован, и это не предосторожность на всякий случай.
Замер счётчиком рендеров через CDP (значения в dev удваиваются StrictMode):

| Действие | Без `memo` | С `memo` |
| --- | --- | --- |
| Выбор строки | 51 строка | 1 |
| Смена выбора | 51 строка | 2 |

Каждая лишняя перерисовка — это ещё и три вызова `Intl`-форматтеров на строку.
Та же граница нужна этапу 3: подсветить ячейки, затронутые живым патчем, можно
только если строка перерисовывается независимо от соседей.

## Состояния UI

Все четыре требуемых состояния обслуживаются на одном уровне — в `app/app.tsx`,
по флагам запроса, а не разрозненно по компонентам:

| Условие | Отображение |
| --- | --- |
| `isPending` — данных ещё нет | Скелет, повторяющий форму дерева |
| `isError` и данных нет | Экран ошибки: причина, пути невалидных полей, повтор |
| `isError`, но данные в кэше есть | Дерево остаётся, сверху полоса «показаны последние загруженные данные» |
| Данные есть, узлов ноль | Пустое состояние |
| иначе | Дерево |

Третья строка — не деталь оформления. TanStack Query при отказе ревалидации
сохраняет `data` и одновременно выставляет `status: 'error'`, поэтому запрос
может быть «ошибочным» и «с данными» сразу. Разводить эти два случая обязан
клиент: подменять рабочий экран ошибкой из-за неудавшегося обновления — потеря
контекста. Фоновая ревалидация сама по себе состояние не сбрасывает, в шапке
появляется пометка «обновление…».

Проверить все пять строк можно панелью отладки (см. README) — она меняет
поведение сервера без перезагрузки страницы.

## Поиск

```
строка ──набор──▶ { name: текст }  ──┐
       ──Enter──▶ POST /api/search   │
                     │               │
                     ▼               │
              Claude, structured     │
              outputs по схеме       │
                     │               ▼
                     └──▶ OrgFilter ──▶ selectRows ──▶ строки таблицы
                                  └──▶ describeFilter ──▶ чипсы
```

Обе ветви сходятся в одном типе `OrgFilter`, поэтому в коде применения фильтра
нет развилки «если AI»: поиск по подстроке — это тот же фильтр с одним
заполненным полем. Отсюда и то, что чипсы, тесты и сортировка написаны один раз
и работают для обоих путей.

Ключ живёт только на сервере: вызов модели идёт оттуда, клиент про провайдера не
знает ничего. Ответ модели проходит валидацию наравне с любым ответом API — см.
[ADR 007](adr/007-ai-search.md).

## Границы слоёв сети

`transport` не знает ни одного доменного понятия: ни `OrgNode`, ни `headcount`,
ни даже пути `/api/org-tree`. Он умеет переместить байты и назвать отказ.
`api` знает ресурсы: какой путь, какая форма ответа, какой ключ кэша.

Зависимость односторонняя — `api → transport`, и это не пожелание в документе:
`shared/transport/layering.test.ts` читает файлы слоя и падает, если в них
появился импорт снизу вверх или упоминание доменного термина. Правило,
за которым никто не следит, живёт до первого рефакторинга.

Именование в `api` — по ресурсу, роль суффиксом: `org-tree.ts` (запрос),
`org-tree.schema.ts` (валидация). Поэтому у AI-поиска из step/4 место уже
определено — `search.ts` и `search.schema.ts`, а не «ещё одна функция в общий
файл схем».

## Стилизация

Только styled-components; inline-стилей в проекте нет. Цвета, отступы,
типографика и пороги эффективности заданы в `app/theme.ts` и типизированы через
расширение `DefaultTheme`, поэтому обращение к несуществующему токену — ошибка
компиляции.

Оформление живёт рядом с компонентом, который его использует, а не в отдельных
`*.styled.ts`. Деление по признаку «styled или нет» разносит по разным файлам
части одного целого и ничего не говорит о том, что куда класть. В `shared/ui`
попадает то, у чего есть самостоятельный смысл и второй потребитель: карточка с
прокручиваемым телом (`Card`, `CardScroll`, `CardToolbar`), переключатель
представлений (`SegmentedControl`), состояния загрузки и ошибки. Раскладка
конкретной страницы остаётся в файле этой страницы.

Признак, что пора выносить, — появление второй копии: `Scroll` был написан
дважды, в `app.tsx` и в таблице, и это стало поводом завести `Card`.

Внутри крупного компонента оформление разносится вместе с разметкой, которой
оно принадлежит, а не в отдельный файл стилей. Так таблица разделена на
`org-table.tsx` (каркас), `org-table-head.tsx` (сортируемые заголовки) и
`org-table-row.tsx` (строка). Деление даёт не только читаемость: строка стала
мемоизированным компонентом, и смена выделения перерисовывает две строки вместо
пятидесяти одной — измерено, см. ниже.


## Развёртывание

```
          :8080
            │
     ┌──────▼───────┐        ┌──────────────┐
     │  client      │  /api  │  server      │
     │  nginx       │───────▶│  node        │
     │  + статика   │  /api/live (upgrade)  │
     └──────────────┘        └──────────────┘
       публикует порт          только expose
```

Наружу торчит один порт: nginx отдаёт статику и проксирует на сервер всё, что
начинается с `/api`, включая апгрейд WebSocket-соединения. Клиентский код при
этом не знает адреса бэкенда — он всегда обращается по относительному пути, и
в dev его так же проксирует Vite.

Образ сервера собирается без шага компиляции: Node снимает типы с исходников
на лету, см. [ADR 006](adr/006-server-without-build-step.md).

Агрегация в итоге легла не в `features/`, а в `entities/org/aggregate.ts`:
это чистая производная от доменной модели, а не поведение интерфейса.
`features/` остаётся для того, чем управляет пользователь — раскрытие ветвей,
сортировка, фильтр.
