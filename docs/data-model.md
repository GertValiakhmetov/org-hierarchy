# Модель данных

## Узел

API отдаёт плоский массив; иерархия выражена ссылкой `parentId`.

```ts
interface OrgNodeDto {
  id: string;
  name: string;
  parentId: string | null;  // null — корень (дивизион)
  headcount: number;        // собственная численность, без потомков
  budget: number;           // собственный бюджет в рублях, без потомков
  performance: number;      // 0–100
  updatedAt: string;        // ISO-8601
}
```

**Показатели узла — собственные, не накопленные.** Отдел с `headcount: 3` — это
три человека руководства отдела, а не весь его штат. Суммирование по поддереву
выполняет клиент; это и есть проверяемая агрегация, поэтому сервер её не делает.

## Инварианты

Проверяются в `shared/api/org-tree.schema.ts` на каждом ответе. Нарушение любого —
ошибка запроса, данные до UI не доходят.

| Инвариант | Проверка |
| --- | --- |
| Все поля присутствуют и имеют верный тип | Пополевая проверка формы |
| `headcount` — целое ≥ 0, `budget` ≥ 0 | Диапазон и целочисленность |
| `performance` ∈ [0, 100] | Диапазон |
| `updatedAt` разбирается как дата | `Date.parse` |
| `id` уникальны | Множество встреченных id |
| `parentId` ссылается на узел из того же ответа | Поиск в множестве id |
| В иерархии нет циклов | Подъём к корню с отметкой пройденных узлов |

Проверка циклов помечает уже проверенные узлы (`settled`), поэтому весь массив
обходится за O(n), а не за O(n·глубина). Один цикл даёт одно сообщение, а не по
сообщению на каждого участника.

## Дерево

`buildTree` разворачивает плоский список в `OrgTree` за два прохода:

1. Каждый DTO превращается в узел и кладётся в `byId`.
2. Каждый узел приписывается родителю либо становится корнем.

Глубина проставляется отдельным обходом в глубину: в плоском массиве родитель
может встретиться позже ребёнка, и вычислить её на первом проходе нельзя.

```ts
interface OrgTree {
  roots: OrgNode[];
  byId: ReadonlyMap<string, OrgNode>;  // доступ к узлу за O(1)
  order: readonly string[];            // порядок обхода в глубину
  size: number;
}
```

- **`order`** задаёт порядок строк таблицы и совпадает с визуальным порядком дерева.
- **Порядок соседних узлов наследуется от сервера** и не сортируется: в ответе
  он осмысленный, алфавитная сортировка его бы разрушила.
- **Уровень выводится из глубины**: 0 — дивизион, 1 — отдел, 2 — команда.
  Отдельного поля в API нет, иерархия остаётся единственным источником правды.

## Эффективность

Пороги заданы один раз в `entities/org/performance.ts` и используются и деревом,
и таблицей:

| Полоса | Диапазон |
| --- | --- |
| `high` | ≥ 80 |
| `medium` | 60–79 |
| `low` | < 60 |

## Агрегация

`aggregateTree` сворачивает собственные показатели каждого узла вверх по дереву
и отдаёт `Map<id, OrgAggregate>`:

```ts
interface OrgAggregate {
  headcount: number;    // сумма по узлу и всем потомкам
  budget: number;       // сумма по узлу и всем потомкам
  performance: number;  // средневзвешенная по headcount
}
```

### Один проход вместо рекурсии

`tree.order` — порядок обхода в глубину, поэтому идти по нему **в обратную
сторону** значит гарантированно встретить каждого ребёнка раньше его родителя.
Родителю остаётся сложить уже готовые результаты детей:

```
order:      div → dep → team-1 → team-2
обратно:    team-2, team-1, dep, div
                            ↑ к этому моменту обе команды посчитаны
```

Отсюда O(n), отсутствие рекурсии и однократный обход. Промежуточные суммы
живут в отдельной карте-накопителе: публичный результат содержит только три
поля, и внутренняя бухгалтерия не утекает потребителям даже в рантайме.

### Средневзвешенная эффективность

```
performance = Σ(performance_i × headcount_i) / Σ(headcount_i)
```

по узлу и всем его потомкам. Простое среднее исказило бы картину: команда из
трёх человек влияла бы на показатель отдела так же, как команда из сорока.

**Вырожденный случай.** Если во всём поддереве нулевая численность,
взвешенное среднее не определено — делить не на что. Тогда берётся обычное
среднее арифметическое собственных показателей узлов поддерева. Поведение
закреплено тестом `falls back to a plain mean when the whole subtree has no staff`.

### Собственное против суммарного

| Где | Что показывается |
| --- | --- |
| `OrgNodeDto.headcount` | Собственная численность узла |
| Дерево | **Суммарная** — иначе «Инженерия · 5 человек» вводит в заблуждение |
| Подсказка в дереве | Разбивка: собственных N, в подразделениях M |
| Таблица, «Всего сотрудников» | Суммарная |

## Контракт WebSocket-патча

Канал: `ws://<host>/api/live`. Сервер шлёт два типа сообщений.

```ts
type LiveMessage =
  | { type: 'hello';        version: number }
  | { type: 'node-updated'; version: number; patch: OrgNodePatch };

interface OrgNodePatch {
  id: string;
  headcount?: number;   // отсутствующее поле означает «не менялось»
  budget?: number;
  performance?: number;
  updatedAt: string;
}
```

Патч частичный: приходят только изменившиеся поля. Это же множество полей
определяет, какие ячейки подсвечиваются.

### Зачем `version`

Счётчик изменений с момента старта сервера. При подключении приходит `hello` с
текущим значением, и клиент сравнивает его с последним виденным:

| Условие | Действие клиента |
| --- | --- |
| Первый `hello` | Запомнить версию, ничего не делать |
| Версия совпала с последней виденной | Ничего не делать — за время обрыва данные не менялись |
| Версия отличается | `invalidateQueries` — в потоке был пропуск |

Это прямо отвечает требованию «инвалидация кэша только при реальном изменении
данных»: переподключение само по себе рефетча не вызывает.

### Проверка на клиенте

Кадр проходит ту же границу доверия, что и REST-ответ:
`parseLiveMessage` в `shared/api/org-tree.schema.ts` разбирает JSON и проверяет
форму. Некорректное сообщение отбрасывается с записью в консоль и **не попадает
в кэш** — испортить данные, которые пользователь уже читает, хуже, чем
пропустить одно обновление.

## Частичный пересчёт агрегатов

Патч приходит в кэш как новый массив узлов, поэтому дерево пересобирается
целиком — это O(n) и структурная операция. А вот свёртка показателей
пересчитывается только по цепочке:

```
patch → узел «Ядро платформы»
         ↑ пересчитан
       отдел «Платформа»
         ↑ пересчитан
       дивизион «Инженерия»
         ↑ пересчитан
       остальные 48 узлов — перенесены из предыдущего снимка
```

`OrgAggregates` хранит рядом с публичными значениями промежуточные суммы
(`weighted`, `performanceSum`, `nodeCount`), поэтому родителю достаточно сложить
уже готовые результаты детей — подниматься до листьев не нужно. Сложность
пересчёта O(глубины) вместо O(n); копирование снимка остаётся O(n), но это
перенос ссылок, а не вычисление.

Новый экземпляр возвращается намеренно: потребители сравнивают агрегаты по
ссылке, а мутация на месте сломала бы мемоизацию и оставила бы прошлые снимки
с изменёнными значениями.
